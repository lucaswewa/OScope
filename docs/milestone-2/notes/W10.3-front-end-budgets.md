## Summary

The app's speed and size, measured beside the server's by `cargo xtask perf --web`, against budgets set from what W1.5, #113 and W6.4 measured ([spec](../phases.md#w10-3), [ADR-0059](../../adr/0059-front-end-budgets.md)):

- **The live view:** at least 12 frames a second, and a frame on the page at most 100 ms after its exposure, at 1920 × 1272 in mode `design`.
- **The first frame after opening the app:** within 2 s.
- **A full-screen view never seen, deep-zoomed:** sharp within 150 ms, the median of 20 jumps.
- **The bundle, gzipped:** its entry at most 100 kB, its largest chunk at most 300 kB, all of it at most 1,200 kB.
- **The memory over a long live view:** growing by at most 10 MB an hour, by Theil–Sen's slope, as P53's soak reads the server's.

`cargo xtask soak --web` keeps the live view open as long as the soak, and the nightly soak's workflow runs it so.

## How to try it

On the owner's PC, its release server running from `target/release`, so in a build folder of the run's own:

```sh
npm --prefix web ci
CARGO_TARGET_DIR=target-perf cargo xtask perf --quick --cuda --web
```

It prints each budget and its measure, and writes `target-perf/perf/report.html`. Lower a budget in `xtask/src/perf.rs` below what was measured, `web.live.fps`'s to 20 say, and run it again: the run fails, saying which.

## Design notes and deviations from the plan

- **The suite prints, and xtask judges,** as the server's benchmarks do: one report, one place for the bounds. Run alone against the debug server, `npm run test:perf` prints its measures, and judges nothing.
- **Node runs the tools' own scripts,** Vite's and Playwright's: npm's and npx's are batch files on Windows, which a program can't start as it starts `cargo`.
- **The rate and the latency are the readout's,** the live view's own window over its frames: ten readings a second apart, their medians.
- **The first frame is timed in the page,** from the navigation's start to the readout's first *Live*, the camera already streaming.
- **The memory is the heap after a collection,** Chromium's own count through its DevTools protocol, every 15 s; the first quarter is left out, while caches fill.
- **The release build is xtask's,** into the build folder it is given: the owner's release server runs from `target/release`, and Windows won't replace a program that runs.

## Tests

- **Unit, 6 new:**
  - xtask: the app's budgets read from `perf:` lines and judged; one broken, the live view's rate or the bundle's entry, failing the run; the memory's growth judged in a whole run and not a quick one;
  - the slope, 5: a line's own slope; a steady series flat though a few samples are far off it, where a mean of the slopes would follow them; a slow leak found under noise; none without two points; and the steady part after the first quarter.
- **The suite,** against the debug server and the release one: its five tests passed, each measure printed.
- **A budget broken on purpose fails the run:** the unit test above, and the quick run's own failure on the server's post-stitching.
- **Mutation checks, 5, all caught, none hung:** the live view's budget raised to 20 fps; a quick run judging the memory; the bundle's entry unbounded; the slope a mean of the slopes; and the steady part the whole series.
